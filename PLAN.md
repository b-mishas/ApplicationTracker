## M7 implementation plan — recovery simplification

**Decision direction:** retain the core safeguards; prefer existing checkpoints, source evidence and unfinished work over another pending-work store. Historical scope reconstruction, selection journals and generic orphan handover verification are provisional. Freeze additional recovery features until this comparison is complete; allow fixes needed to preserve data or run the agreed scenarios. No runtime mechanism is removed by this plan.

Keep setup decisions and dependency-aware approvals, the editing guard, revision-checked workbook changes, storage self-check, journalled checkpoint reset and installation/scope/setup-discovery run tags. Preserve the separation between personalization readiness, scheduled-operation verification and search progress. Recovery backlog should report partial/recovery required with a concrete next action; it must not automatically block otherwise safe searches. Editing, stale approvals and unfinished/malformed resets still require their safety gates.

### Candidate simplifications and limits

- **Current checkpoints first.** Claude's employer A/B example works for an ordinarily overdue A: interruption leaves its successful date old, and adding B clears B's date. Evaluate deriving progress from applicable checkpoints, current due work, unfinished source work, open finds and unresolved execution evidence. Do not require every source to be checked after the latest selective reset: unchanged sources legitimately retain earlier success. Conversely, a nonempty date/Gmail checkpoint proves neither current coverage nor completion of the required interval. Define the initial-search target separately from recurring due work, including portal rotations, gap searches and per-run limits.
- **Close the actual retry gap.** The routine forces employer/portal retries even when not due. An old valid date can therefore conceal a newer failed or unattempted forced check. `previousRetry` skips folders without finish.json; those folders may have no retry list to union. Reconcile saved selections/outcomes and unfinished work from interrupted runs, retiring obligations only after a qualifying success. An unrelated finished run is not automatically a safe history cutoff. Prefer extending existing records narrowly; add new persistent state only if an outcome test demonstrates the need.
- **Reduce ordering machinery if proven safe.** Try run identity/order and existing due/evidence records instead of a separate selection journal. "Same run or later" is insufficient when a run is resumed or selects new work after an earlier success. Test both orders explicitly. Remove selection-specific precision requirements only with the mechanism they support; other evidence reconciliation may still need ordered timestamps. Do not round or rewrite legacy evidence to make it pass.
- **Simplify attended orphan recovery.** Prefer a compact acknowledgement of verified-empty content or takeover into an identified run, with pending work retained. Preserve original payloads, including saved results not yet captured in a ledger; capture-before-selection is a rule, not proof it executed before a crash. A marker alone must not certify extraction or delivery. Test removal of per-file copies/hashes/transfer checks; retain only checks with demonstrated benefit. Missing or changed evidence must yield actionable recovery/partial reporting, never silent completion. Do not delete runtime evidence when retiring code.
