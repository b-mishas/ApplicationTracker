## Planned improvements

1. **State-driven search orchestration.** Follow [agent/orchestration/ORCHESTRATION_ROADMAP.md](agent/orchestration/ORCHESTRATION_ROADMAP.md). Milestones 1–13 are done: the full helper was replaced by the read-only `app/capture-check.mjs` and the agent's own run ledger (full helper kept in commit 92e1d73). Next: observe 2–3 ordinary scheduled searches (what `--open` lists at start and finish, whether Not done agrees, cost).
2. **Enforce the finish and reassess rules in code.** Two capture-check fixes (a311937) rely on routine wording: the finish check over all runs, and `reassess` overriding a dropped-list `known`. In the observed scheduled searches, compare each summary's Not done with `--open`, and check whether `reassess` finds were rated again. If either fails: have `check` print `reassess` itself for a dropped match whose newest ledger entry `--open` would list, and consider having `--open` write a small finish record that the summary must cite. `app/finish-run.mjs` (2026-11-24) now writes finish.json with a retry list the summary cites; check in the first real run whether Not done matches it.
3. **Same vacancy as a LinkedIn alert and on the employer board.** Their URLs differ, so capture-check reports `similar`, not `repeat`, and the agent must judge. Once the link finder or a reading resolves an alert to the employer's posting, let the ledger line keep both URLs (for example `postingUrls`, as jobs.json records already do) and have capture-check index those aliases, so later finds of either URL are `repeat` or `known`. Test with a same-title second requisition that must stay separate.
4. **Employer model comparison.** Before relying on the smallest model for career pages, compare it with the middle model on simple, paginated and JavaScript-heavy sites (including zero-result ones) against independently inspected listings; measure openings found, partial/errors and actual run cost.
5. **Rehearsal regression cases.** The next rehearsal must find the two openings the Terra rehearsal (2026-11-18) missed: Zalando's second listing page (Software Engineer (Kotlin), Transport Planning Optimization, 2723609) and n8n's JavaScript-only Ashby board (Senior Product Engineer (TS/NodeJS/Vue)), or record them as partial with the limit reached.
6. **Board script (deferred agent work).** Port JobTracker's fetch-boards.mjs only after designing and testing: durable pending discoveries before IDs are marked seen, re-evaluation after filter changes, changed or reopened jobs with known IDs, explicit partial status at pagination limits, bounded resumable first run, kept state on fetch failure, no closure from absence, ambiguous city-only locations kept for review. Then decide app/ or scripts/ and the write permissions. Verify network access in scheduled Claude and Codex runs first.
7. **In-app button tutorial.** Highlight one control at a time against a translucent overlay. Give each a one-sentence explanation and provide Next, Back, Skip and replay. Support keyboard use and narrow screens.
8. **Versioned ZIP names (optional).** The footer now shows package.json version; future packages include BUILD_INFO.json with version and build time. Consider adding the version to archive names too.
9. **Closure seen only on a banner.** The importer accepts Open/Closed only with "Posting reviewed" (import-discoveries.mjs line 67), so a posting that shows only a closure notice stays Unverified and is flagged (Part B §6). Decided 2026-11-24 (user): keep this behaviour, although JobTracker and Codex's review would accept an explicit notice. Revisit only if flagged banner-only closures become a burden; then separate availability evidence from assessment basis in the importer, add a regression test and change §6. Never label a banner as a reviewed description.
10. **Later.** Backup recovery and updates that preserve local data, signed launchers, agent urgency suggestions, and possible UK/GB normalization. Coordinate agent-facing schema changes with Claude.
