### Completion

Your context is compacted automatically. Completeness is defined by the checklist below, not by run length or tool-call count. Work economically: do what is due today, reuse cached methods, and leave what is not due for its own run.

This checklist is for acceptance; §2 sets the work order. The run is complete only when every item below is accounted for as done, not due, deferred by a limit in this prompt, partial after a limit, or failed with an observed tool error after one retry:

2. Every result page of the Gmail interval fetched, and every alert mail in it processed.

4. Re-checks and Shortlisted refreshes due today done (§5).

6. Every portal and coverage-gap search due today checked (§5).

#### Capture check (required before any reading)

Never deduplicate or shortlist finds with your own script or by eye, and select no posting to read until its find is in the ledger with the check's result; this holds with an empty jobs.json too, because the check also catches the dropped list and repeats within the run. Before opening or rating any find (alerts, employer pages, portals, link finder), check it with `node app/capture-check.mjs --seen data/reports/runs/<run-id>/run-ledger.jsonl <file>` from ROOT (several files allowed), then add it to the ledger: pass subagent result files as they are, and for finds you extracted yourself the JSON-lines file you wrote. It compares the finds with jobs.json (records of any status), the coverage.json dropped list, today's ledger and the earlier finds of the same call, and prints one line per find, so do not print a file before or after checking it. `known` finds share the company and the provider job ID or posting URL (ignoring tracking parameters), or the identical posting URL under a variant of the company name, with the record or dropped entry it names: record them in the ledger as duplicate with that record ID and status, do not read or rate them, and report relevant existing applications under Flags. A `known` find matched to a dropped entry is still read or rated if `--open` lists it as `reassess`. `repeat` finds share the provider job ID or posting URL with the named find of today's ledger or of the same call: the same vacancy from another source; add their source to that find's ledger line instead of a new line (a repeat is not a decision and never closes it), read and rate the vacancy once, and add the other source to its batch record. `similar` finds share only company and title (allowing a company suffix or a title ending in its own city) and, where both have one, location (a shared city name counts, in any spelling such as Wien and Vienna) with the named record, dropped entry or find, or share a URL or job ID under another company label (marked so: one board page can list several employers, and job IDs repeat across ATS tenants); decide yourself whether they are the same vacancy. A `similar` find that is the same vacancy as a dropped entry counts as "previously dropped". `new` finds are everything else. The check writes nothing; keep the ledger yourself. A find decided in an earlier run keeps that decision unless `--open` lists it as `reassess`; reuse it without reading it again. Read and rate only `new` finds and the `similar` ones you judge to be different. Count `known` finds matched to a dropped entry as "previously dropped". Shortlisted records are reopened by the refresh rule, and those saved as "Title only" or Unverified by "Re-checks" (both §5). Other records need reopening only for a material update.

### 3. Scope

Apply the profile's countries, remote rules, role families, seniority rules and preferred regions. Where profile §4 makes relocation or on-site limits hard, drop and count roles that break them; where they are preferences or not stated, keep the role and note the constraint in gaps (§6). "Remote" does not imply worldwide eligibility; if eligibility is unclear, flag it. Apply the profile's special rules (§9) exactly as scoped there; they take precedence over the general drop rules.

Drop and count clear mismatches using the profile's mismatch signals. Drop without opening only when the title and alert text establish the mismatch; otherwise read the description. Do not reject on a keyword alone; judge whether the missing experience is essential and central.

Work authorization: profile §1 says where the candidate may already work. For an in-scope role in any other country (including remote roles restricted to it), read the posting for terms such as "right to work in …", "must be eligible to work in …" or "no visa sponsorship". Drop roles that require existing authorization or exclude sponsorship, and count them separately under Coverage. If sponsorship is offered, keep the role and note "visa sponsorship offered" in gaps; if the posting is silent, keep it and note "work authorization not stated". Never drop on this ground without reading the posting text. Leave existing New/Shortlisted records unchanged and report them under Flags.

A different vacancy at an employer the user already applied to may qualify; mention the existing application under Flags.

### 4. Gmail alerts

- Interval: the label from Part A, from `gmailCheckedThrough` in coverage.json minus one day (without a checkpoint, the earliest `gmailInterval.from` in run-completion.json of an earlier unfinished run, else the run's start minus the first-search days from Part A, 30 when Part A has no whole number of at least 1; up to fourteen for a known gap, and report any longer uncovered interval) to the run's start time. A mail may be skipped unopened only when its subject names a single job that is already in jobs.json or on the dropped list. Open the body of every other mail and extract title, company, location and the posting link for each job in it (alert links usually wrap a job ID, e.g. LinkedIn `/jobs/view/<id>`). Subject-line triage is not processing.
- Label sources by alert service as listed in the profile (e.g. "LinkedIn alert"). An employer's own job-alert mail gives alert finds ("Employer alert"); it is never a check of that employer and never sets its "Last checked".
- Some alert mails carry no per-job links. Send each job in them that looks relevant to the link finder (§1). If that finds nothing, record it in the ledger as excluded with reason "unresolved: no link" (finish-run.mjs adds it to `dropped`) and treat it as processed.
- Advance the checkpoint to the run's start time when every page and every mail in the interval has been processed and every resulting candidate is rated, saved in a batch or on the dropped list. Unreadable postings and unresolved jobs without links do not hold it back. An empty successful scan advances it; unfetched pages or unopened mails do not. Distinguish an empty result from a failed connector.

### 5. Reading postings and checking sources

Reading sequence for every candidate, employer/ATS access first, with at most one link-finder round per candidate per run (§1):

0. If only a LinkedIn or otherwise inaccessible board link is known, first run the link finder, or its company-and-title searches yourself, to find the employer's posting. A search result alone is not a reviewed description.
1. Read the employer career page or ATS (Greenhouse, Ashby, Lever, Workday, SmartRecruiters, …) via web fetch or public job-listing/detail endpoints. Listing titles alone do not count as reading descriptions.
2. If JavaScript is required, fetch is blocked, results are only a shell, or pagination cannot be followed through fetch, discover and actually attempt an available browser read-only. A successful HTTP response or search-engine snippet is not proof of complete listings. For employer/portal checks, reserve time/calls for this fallback within the existing fifteen-call/five-minute limit; never extend the limit. If it is already exhausted, record partial/deferred with that limit, not a browser failure. If browser tools are unavailable, record the discovery result; if attempted, record the URL and actual error.
3. If no readable employer posting was found, read the board posting with the browser tested in Setup, following the sign-in rule. LinkedIn job pages: never web fetch; read the full description with text/accessibility tools, no screenshots. Reuse your posting tab for sequential reads; only navigate and expand descriptions, never use application or engagement controls.
4. If still unreadable and no finder round was attempted for this candidate this run, perform one, then read any matching employer URL by 1–2. If unresolved, save it as Title only / Unverified (§6) and record observed errors; failed access never proves closure.

Shortlisted refreshes: a Shortlisted record is due when its `refreshed` entry (coverage.json) has no `lastConfirmedAt` (a missing entry or an older plain date counts as that date), when that date is at least three calendar days old (Part A time zone), or when its verified deadline lies from today through ten days ahead and it was not confirmed today. Follow the employer-first reading sequence above: is it still open, did the deadline or content change? Update the record through the batch. Write one line per record checked to `refresh-<n>.jsonl` in the run folder: `jobId`, company, URL, `result` (open, closed, changed or unconfirmed), `text` (as for postings), error; and one source-evidence line (`kind` refresh). finish-run.mjs sets `refreshed` from these lines; never write it yourself. A failed read is `unconfirmed` and counts as failed. If the record is also due for a re-check, one read serves both. A record whose re-checks stopped at three attempts is not read for a refresh; report it as unresolved under Flags. A passed deadline is flagged (§7) and does not prove closure.

Re-checks: each run, re-check up to five "Title only" and up to five Unverified records with status New or Shortlisted. Take first those with the fewest attempts in `recheck` (coverage.json), then the oldest last attempt; skip records with three attempts. For each: follow the reading sequence above. Then:
- Add one attempt to the record's `recheck` entry, whatever the result.
- Posting read: update the record through the batch (assessment basis, availability with its evidence, employer URL, fit) and remove its `recheck` entry.
- Still unresolved at the third attempt: report it under Flags as "could not be verified after three attempts" and keep the entry. Do not re-check it again unless an alert, employer check or portal shows the job again.

Never retry a failing access method more than once. Report the observed failure accurately; do not guess at its cause. Never browse sources the profile marks as "alerts only". Using a career site's own search or filter (including the read-only search requests its page makes) to list openings is allowed; submitting any other form is not.

Employers: use the employer schedule in the profile; without one, an employer is due when its last successful check is at least 3 calendar days old for priority A, 7 for B, 14 for C. The last successful check is the newer valid date of the workbook's "Last checked" and coverage.json `employers[].lastChecked`. An empty date is due; an invalid or future date is also due and goes under Flags. Order due employers by next-due date (last check plus interval), oldest first; never-checked employers come first, ordered by oldest `lastAttempt` (none first). Break ties A before B before C. Attempt at most twenty employers per run, failed and partial attempts included; the rest are deferred to the next run. Set `lastAttempt` to today for every attempted employer. Before checking, write today's selected employers, due portals and gap searches and the carried `employer`/`portal` retry items to `due.json` in the run folder (including those deferred by a limit): `{"employer": [names], "portal": [names]}`, names exactly as in your source-evidence lines; finish-run.mjs reports each one without an evidence line.

Check each employer's relevant listings with its cached `method` in coverage.json, if any. If that fails or no longer covers the scope, rediscover once within the same limits; keep the old method if rediscovery fails. Save a new or changed method only when it listed the whole intended scope. A method is one short line: ATS or site, public search or API URL, filters or query, paging and how the end of the list was recognised; never code, credentials or text copied from the site. A cached method does not prove today's check.

Account for every employer selected for this run under its exact workbook name, comparing that list with source/delegated results. Missing results, absent cached methods, name mismatches and skipped/unsupported access methods are unchecked, not successful zeroes. Resolve names and verify the real careers board where possible. Check remaining employers through listing subagents or yourself within the same per-employer and per-run limits, including the five-missing-URL limit below; fallback does not reset those limits. Record unresolved employers as partial, deferred by the actual limit or failed with the observed error, keeping them due.

Fill missing career URLs for at most five employers per run, priority A first; find them by web search, never by guessing URL paths. Report how many remain missing. Finding a URL is not a check of its listings. After successfully checking an employer's listings (evidence status checked), record the date of that check in coverage.json `employers` and in the workbook's "Last checked" cell, never replacing a later date already there; a blocked or incomplete check does not count; store newly found career URLs the same way ("Careers page"). Write workbook cells from ROOT with `node app/employer-workbook.mjs update --input <absolute path of a temporary UTF-8 JSON file>`: an array of objects with `Company` (the exact workbook name) and only the fields you change, `Careers page` and/or `Last checked` (YYYY-MM-DD), because an empty value clears that cell. If the helper is unavailable or the workbook is locked (open in Excel), write coverage.json only and say so once under Coverage. Never rebuild the workbook or change its "Status" column.

Portals: cover postings since each source's `lastSuccessfulCheckedThrough` with a one-day overlap; without one, the first-search days from Part A. Do not discard an older relevant vacancy that is confirmed open. Failed, skipped, partial or deferred searches never advance coverage (§10). In a list sorted newest first, a page holding only postings older than the window (a single old pinned or sponsored item does not count) confirms the end, even when the stated total is larger; this date cutoff holds only when the list is sorted newest first, each page rendered completely and its dates are usable; otherwise read on. A list that cannot be sorted by date needs all its pages. Before counting a keyword search, check that the keyword filters: if the results equal the unfiltered list, read the unfiltered list by date instead and note "filter not applied" in the evidence.

Portal progress is kept per country page set or search term, so a partial portal resumes instead of starting over. Each portal's evidence line carries `progress`: `{"<country or term>": {"lastFullPage": 3, "oldestSeen": "YYYY-MM-DD", "newestId": "<ID or URL of the newest ordinary posting>", "complete": false}}`; copy it into that portal's `progress` in coverage.json `sources`. A page counts as full only when it shows as many items as stated or as the site's page size (the last page excepted); a page showing fewer is retried once and otherwise stays incomplete. Each run, first read each entry newest first from page 1, since new postings push older ones to later pages. Read every page in full and assess pinned, sponsored or featured results like any other; leave them out only when choosing or finding the stopping marker. Stop after the page that holds the entry's `newestId`; without one, or when that posting no longer appears, stop only at the date boundary above. Record the newest ordinary (not pinned) posting as the new `newestId`. Then continue an incomplete entry from one page before its `lastFullPage` (overlap) until the window ends. An entry marked complete only needs that newest-first pass.

Coverage-gap searches (profile): weekly unless the profile states another frequency, on the day the profile names (default Monday). Each is a source in coverage.json; it is due on its day and on any later run while its last successful check is at least seven days old or missing, so a missed day is caught up on the next run.

### 6. Verification and fit

- "Posting reviewed": you read the job description.
- "Title only": only after a reading attempt failed this run. Fit provisional or null, availability Unverified, linkType "search" when no direct posting URL exists, and gaps starting with "Posting not read: <observed error>". Such a candidate counts as processed; never leave candidates only in `unfinished`.
- "Open"/"Closed": needs actual posting evidence and a direct posting URL. "No longer accepting applications" is closure evidence. If only a closure banner is visible (no description), keep availability Unverified and report the closure under Flags.
- "Unverified": availability not established. Absence from search results never proves closure.

Assessment basis and availability are separate fields; obey the importer's evidence rules. Never label a record "Posting reviewed" when you saw only a title or a closure banner. Keep relevant Unverified candidates in the import and show their status in the summary. Do not add clearly closed vacancies as new; update existing records when closure is evidenced and the schema allows it.

Fit: rate with the fit scale and bridgeable-gap rule in profile §8. Fixed frame: integers 1–5, 5 is best, null when not assessable; 3 or higher means worth the candidate's attention and counts as relevant. Fit measures skills and level only; never adjust it for country. Use the profile's strengths, confirmed gaps and calibration examples as reference points, not mechanical scoring rules. Never present literature familiarity as hands-on experience.

Reasoning: at most two sentences of specific matching evidence. Gaps: missing requirements marked essential or desirable, plus practical constraints (relocation, on-site days, contract length), kept distinct from skill gaps; list only requirements the candidate does not meet, never a met one (even marked "met"); do not repeat the reasoning. Preserve advertised titles, location restrictions and evidence.

### 7. Deadlines

Look for explicit application deadlines in reviewed postings. For New or Shortlisted vacancies, a verified deadline from today through seven calendar days ahead (Part A time zone, inclusive) is urgent; account for any stated deadline time and time zone, and never flag a passed deadline as upcoming. Do not infer deadlines from posting age; "open until filled" is not a deadline; a passed deadline alone does not prove closure.

Include a verified deadline in the optional batch field `applicationDeadline` as `YYYY-MM-DD`; omit it when unknown. Never infer a date from posting age or use relative wording. Batches still do not accept `urgent`; do not add it, call the tracker's web API or edit jobs.json. Report under Flags:
- **URGENT — YYYY-MM-DD:** Company | Title | URL
- **Deadline passed — YYYY-MM-DD:** Company | Title | URL (existing Shortlisted records only; do not close them)

### 8. Duplicates

Strong identity evidence: provider plus requisition ID, the same direct posting, or clear evidence that two listings describe the same vacancy. Similar company/title only triggers a comparison (ignore gender suffixes such as "(m/w/d)"; an employer may rename a title or list another city, so such differences call for a comparison, not a verdict either way); keep seniority and location distinctions; different requisition IDs normally mean different vacancies.
- Confirmed existing vacancy: send `matchesRecordId` with its id.
- Clearly distinct: add a new record.
- Uncertain: omit it from the import and report both links under Flags.
Do not delete records or replace reviewed information with guesses.

### 9. Batches and import

A top-level batch in `data/incoming/` without a matching `data/reports/<batch filename with final .json removed>.report.json` is pending; ignore `data/incoming/imported/`. Use the report path returned by RESULT after import; for example batch 2026-11-05-example.json creates 2026-11-05-example.report.json. Also inspect reports for unresolved rejected or ambiguous outcomes from any earlier run; a report's existence does not prove complete success. Fix only errors you can establish confidently.

Write one new UTF-8 batch `data/incoming/YYYY-MM-DD-<runId>.json` (local run date; unique runId equal to the envelope's runId; UTC timestamps ending Z). Follow batch.schema.json exactly. Each `sources[].file` equals this batch's filename. Each source may optionally carry `linkType` "posting" or "search" when known; a source matching the primary URL must agree with the vacancy’s `linkType`. Omit unknown source types. Include provider and providerJobId together when known. `postedDate` must be a valid `YYYY-MM-DD` calendar date or empty if unknown. Convert unambiguous relative wording (e.g. “3 days ago”) against the date of `observedAt` in Part A's timezone; for hours, subtract the elapsed hours before converting to that local date. Keep the original wording and observation time in source evidence. Leave ranges, month-only dates and ambiguous ages empty; never use the search window or the day you found it. Use country codes for the actual advertised countries, including eligible remote roles outside the profile’s usual geography. Use an empty countries array only when the country is genuinely unspecified; preserve the real location in locationRaw/workModeRaw and never substitute an incorrect code. An empty jobs array is valid.

If this environment uses another time zone, set the standard process environment variable TZ to Part A's IANA time zone for validation and import so calendar dates match the user's local day; no tracker time zone setting exists. Verify it in the same shell with the same Node: `node -e "console.log(Intl.DateTimeFormat().resolvedOptions().timeZone)"`. On Windows set it in PowerShell (`$env:TZ = '<zone>'`); Git Bash can drop TZ for Windows Node. Import from `app/`:
```bash
# --validate-only checks the batch without importing; --root points to the data folder
node import-discoveries.mjs incoming/<file>.json --root ../data --validate-only
node import-discoveries.mjs incoming/<file>.json --root ../data
```
If ROOT is mounted elsewhere (Claude), use the real mounted path for `--root`.

Run validation and import separately; validation exit 5 must not stop the import of valid records. Exit codes: 0 processed (check ambiguous); 5 partial (repair rejected records); 2 nothing imported; 3 locked (wait one minute, retry once); 4 write failure. Read the RESULT line. If an import was interrupted or its outcome is unclear, rerun the same batch: accepted records match idempotently. Never remove locks, bypass validation, change content merely to evade an error, or edit jobs.json.

Archive a batch into `data/incoming/imported/` (mv; create the folder if needed; never delete or overwrite) only after exit 0, an existing report and no unresolved outcomes. When repairing a batch, keep its filename and runId, revalidate and rerun; never retry unresolved ambiguous records blindly. If import stays impossible: "IMPORT FAILED: <exact error>", keep the batch, list the findings anyway.

### 10. Coverage checkpoint

At the end, update `data/reports/coverage.json` (write a temporary file next to it, check that it parses as JSON, then rename it over the original); keep entries and successful checkpoints for sources not completed this run. Failed, skipped or partial scans never replace an earlier successful checkpoint.

```json
{
  "updatedAt": "<UTC Z>",
  "gmailCheckedThrough": null,
  "gmailLastAttempt": {"attemptedAt": "<UTC Z>", "status": "ok|partial|failed|skipped", "reason": ""},
  "linkedinAccess": {"attemptedAt": "<UTC Z>", "browser": "", "status": "ok|failed|skipped", "postingsRead": 0, "postingsFailed": 0, "reason": ""},
  "sources": {
    "<source name>": {"lastSuccessfulCheckedThrough": null, "attemptedAt": "<UTC Z>", "status": "ok|partial|failed|skipped", "candidates": 0, "relevant": 0, "reason": "",
                      "progress": {"<country or term>": {"lastFullPage": 0, "oldestSeen": null, "newestId": null, "complete": false}}}
  },
  "employers": {
    "<company exactly as in the workbook>": {"lastChecked": "YYYY-MM-DD", "lastAttempt": "YYYY-MM-DD", "careersUrl": "", "method": ""}

  "recheck": [
    {"jobId": "<id in jobs.json>", "attempts": 1, "lastAttempt": "YYYY-MM-DD"}

```
If LinkedIn access testing is excluded, use status skipped, attemptedAt null, zero postingsRead/postingsFailed and the actual exclusion reason; do not label an untested source failed.

Keep exactly this structure and add no other fields: `gmailLastAttempt` and `linkedinAccess` are objects, and every source entry has all six fields (portals also `progress`, §5). Reuse an existing source name instead of adding a second entry for the same source. Replace null only when successful coverage is established. Counts describe this attempt. `relevant` = reviewed candidates with fit ≥ 3. Candidates saved in a pending batch count as processed; noticed-but-unassessed ones do not.

`dropped` remembers roles between runs. Never edit it yourself: finish-run.mjs (§11) appends every `excluded` ledger line not yet listed, with the line's reason, and removes entries older than 60 days. `recheck` counts re-check attempts per saved record (§5); a record without an entry has no attempts yet. Remove an entry when its record is resolved or no longer New/Shortlisted. `refreshed` holds, per Shortlisted record, the last refresh attempt and the last refresh that confirmed its state (§5); finish-run.mjs writes it and removes records no longer Shortlisted. In `employers`, `lastChecked` changes only after a complete successful check, `lastAttempt` after every attempt, and `method` as described in §5. A field missing from an older file means empty; keep all existing entries. `unfinished` holds work that failed with an observed tool error or was left partial or deferred by a limit, each with its reason; remove an entry only when it is completed. Standing rules from the user belong in the profile, never in coverage.json.

### 11. Summary

When finishing, after the import, run `node app/capture-check.mjs --open` (all runs, before closing earlier ones): decide every find it lists, or report it under Not done; never write "nothing" there while it lists a find. Finds left open stay listed for the next run. Then, after your last own write to coverage.json, run `node app/finish-run.mjs <run-id>` from ROOT. It sets `refreshed`, appends `dropped` and writes `finish.json` in the run folder: `searchCoverage` (complete or partial), added records per source, ledger states, reading attempts (`ratedWithoutFull`, `noAttemptRecord`), link-finder results, refreshes (confirmed, unconfirmed), the latest outcome per source, due sources without evidence, and `retry`, the list the next run carries. Before the summary, read each posting in `ratedWithoutFull` and `noAttemptRecord` (recording the reading) and redo its decision, and retry once each source in `withoutError` (partial or failed with no observed error; a new evidence line with `at`); then run the script again. Whatever stays is reported under Not done. Then set `status` "finished" in this run's run-completion.json and in each earlier unfinished run you took over (§1), adding `takenOverBy` with this run's ID there (create a run-completion.json with `runId`, `status` and `takenOverBy` where it has none), and take counts from the ledger, jobs.json and the importer report instead of recounting from memory: the positions added this run are the jobs.json records whose first source is this run's batch (finish.json `import`, with the source each came from; also finds carried from earlier runs, and correct after repeated imports). Postings read N counts this run's ledger decisions with basis "Posting reviewed", title-only N those with "Title only"; ratings carried from earlier runs are not reads. Take source outcomes per kind and status from finish.json `sources`, link-finder and refresh counts from finish.json, and subagent counts and models from run-completion.json.

Terse, telegraphic Markdown in the Part A language; no copied job-description text. Use exactly the four sections below, always all four, in this order, with the table columns as given, and add no others; write **Flags — None** when there are no flags. Every position newly added this run appears exactly once in the table; no row limit.

**Import** — **Result:** added N | updated N | unchanged N | ambiguous N | rejected N (or **Partial import:** counts + report path / **IMPORT FAILED:** exact error). **Search coverage:** complete / partial (finish.json `searchCoverage` after its last run, which counts every find `--open` lists; partial names the number of `retry` items). **Gmail:** OK (date range) / empty (date range) / partial / not read: reason. Added N is the number of positions added this run (see above); the other counts come from the latest importer report.

**New positions** — one table, fit descending, unassessed last; within equal fit: reviewed Open, reviewed Unverified, title-only:

| Fit | Company | Position | Location | Availability | Assessment | Main gap / constraint |
| --- | --- | --- | --- | --- | --- | --- |
| 4 | Company | [Advertised title](direct-posting-url) | City / remote restriction | Open | Reviewed | few words |

Availability and Assessment as actually saved. Fit: the number, "N provisional" for a title-only estimate, or "Not assessed". Newly added Closed records (normally not added) go last and are flagged. For fit 1–2, "Main gap" gives the reason for the low rating. Keep links clickable; escape `|` in titles. If nothing was added: "No new positions added".

**Flags** — urgent/passed deadlines; uncertain duplicates; rejected records; closures of Shortlisted records; records that could not be verified after three attempts; existing New/Shortlisted records requiring work authorization the candidate lacks; material title/location changes; relevant existing applications. Do not repeat new positions here unless a flag needs attention.

**Coverage** — **Run:** started HH:MM, ended HH:MM UTC · **Alerts:** pages fetched N of N, mails in interval N, bodies opened N, skipped as known N, candidates N, previously dropped N, dropped N (of which work authorization N), unlisted services: … · **Postings:** title-fit ≥3 candidates N, read N, failed N, title-only N · **Link finder:** sent N, found and matched N, not found N · **Refreshes:** due N, done N, failed N · **Re-checks:** Title only N, Unverified N, resolved N, given up N · **Employers:** due N, attempted N, checked N, partial N, failed N, deferred N, new openings after duplicates N, methods saved N, careers URLs still missing N (dates in workbook / coverage.json only: reason) · **Portals:** due N, checked N, partial N, failed N · **Gap searches:** due N, done N · **LinkedIn access:** browser used / none (observed reason) · **Subagents:** used (number and model per kind) / not available · **Not done:** each `retry` item in finish.json and each other unfinished item with its observed error, user exclusion or exact prompt limit, or "nothing" · **Evidence:** path of the run folder. Keep every counter, zeros included, when saved evidence supports it; otherwise write unknown. Write "not applicable: <reason>" for excluded work. For employers, portals and refreshes, due = checked + partial + failed + deferred; count a source as checked only when its evidence shows a full check. State any mismatch with the importer report.

If nothing could be imported, state "Nothing imported" under Import and put a "Findings not imported" table under New positions; after a partial import, keep saved additions and unsaved findings clearly separate. Never describe an unsaved candidate as added or an unchecked source as covered.

Last, save the summary as `summary.md` in the run folder and complete `run-log.json` there for diagnosing problems: `runId`; `status` "finished"; `assistant` ("Claude" or "Codex"); `models` (the model of this conversation and of each kind of subagent you started); `startedAt` and `endedAt` (UTC, system clock); `access` with `gmail`, `browser` and `subagents`, each "ok", "failed" or "unavailable"; `items` with checklist items "1" to "7", each "done", "not due", "deferred", "partial" or "failed"; `subagents` as a list of {kind, model, count} from run-completion.json; and `errors` as a list of {step (the § number), kind (alerts, employer, portal, posting, import or other), error} for every observed tool error or limit reached. Write each error as the observed message without URLs, company names, job titles or personal details. Put nothing from the profile or the job postings in run-log.json.
